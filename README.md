> Public record of the Molterra security program: the attack corpus, its findings and adaptation register, the penetration-test package and the cryptography review, republished after every accepted change. The committed `attacks.json`, `findings.json` and dossiers are the corpus's output at the published revision.

# Molterra security

Molterra listens to meetings, reads the records a team has connected, and
writes work products from them. That places three kinds of data in our care:
what people said, the credentials that reach their other tools, and the
identities that prove who is asking. This repository is the public account of
how that data is protected, and — because a description of defenses is only a
claim — the executable evidence behind it: **991 authorized attacks run against
the product's own code on every change, each with a recorded verdict.**

It is written for two readers at once. A customer should be able to read the
first half and understand what stands between an attacker and their data. A
security team should be able to read the second half, run the corpus, and
check every number against the commit that produced it.

Some things are deliberately not here. Hostnames, network layout, key-storage
locations, alerting thresholds, the exact phrase lists inside detectors, and
the identity of providers under NDA are withheld, because publishing them would
help an attacker more than a reviewer. Everything that *is* here is stated as
it is practiced, including where the current release falls short of the target.

---

## 1. What is protected

| Data | Where it comes from | Sensitivity |
|---|---|---|
| Meeting audio, transcripts and the facts derived from them | the desktop client, only while a meeting the user chose is in progress | the content of a company's conversations |
| Records read from connected tools (CRM, mail, calendar, tickets, documents) | integrations the workspace owner authorized | the working state of the business |
| OAuth access and refresh tokens for those tools | granted once by the owner | a live key to a third-party account |
| Passwords, login codes, second-factor secrets, sessions, API keys | the account holder | identity |
| Pages the browser extension reads for ranking | the user's own tabs | the user's private browsing |
| Audit and integrity records | generated by the platform | proof of what happened |

Each row has exactly one owner responsible for its lifecycle and a defined
deletion path: tenant purge removes everything a workspace holds; a member's
"forget" removes what that member contributed, with verifiable tombstones. A
datum with no owner cannot be added — a CI audit refuses the migration.

## 2. Defense in depth — layer by layer

### 2.1 In transit

All client, browser-extension and integration traffic is carried over TLS,
terminated ahead of the application. The API accepts browser requests only from
the product's own origin (a fixed CORS allow-list, not a wildcard). Inbound
webhooks from integration providers are authenticated with HMAC-SHA-256 over
the raw body, compared in constant time, and rejected before parsing if the
signature does not verify.

### 2.2 At rest — authenticated encryption, separated per tenant

Credentials and memory content are stored under **AES-256-GCM**, an
*authenticated* cipher: every ciphertext carries a 128-bit tag, and a single
altered bit in the nonce, ciphertext or tag causes decryption to fail rather
than return corrupted plaintext. An attacker who gains write access to the
database cannot use that access to change what the application later reads;
they can only destroy it. Nonces are 96 bits from the operating system's
CSPRNG, fresh per encryption, so two encryptions of the same value never look
alike.

Memory content is not encrypted under one key for everyone. A per-tenant key is
derived from a master key with **HKDF-SHA-256** and a tenant-specific label,
so tenant keys are cryptographically independent: the compromise or export of
one tenant's derived key reveals nothing about another's. The master key is
held outside the database; who can reach it is restricted to named
individuals with a business need, and that access is itself a control in the
trust center.

The datastores themselves are additionally encrypted at rest by the platform,
so the application-layer encryption above is the second envelope, not the only
one.

### 2.3 Tenant isolation — enforced by the database, not by the query

Every workspace's memory lives in tables protected by **PostgreSQL row-level
security**. Tenant reads run inside a scoped connection that sets the tenant
identity for the transaction; the database's policy then filters every row,
regardless of what the application's SQL says. A developer who forgets a
`WHERE` clause gets an empty result, not another customer's data. The policy is
exercised by a dedicated test suite that runs against a real Postgres in CI, and
the repository's engineering rules forbid substituting an application-side
filter for it.

### 2.4 Identity and access

* **Passwords** are hashed with **Argon2id**, a memory-hard function designed so
  that offline guessing is expensive per attempt even on specialized hardware.
* **Email login codes** live for ten minutes, allow five attempts, and are
  throttled per address on resend. Failed attempts are recorded in the audit
  log with the reason.
* **Multi-factor authentication** is time-based one-time passwords (RFC 6238).
  The secret is stored encrypted under §2.2. A successfully used step is
  remembered so a captured code cannot be replayed in its window. The
  pre-MFA challenge token is signed under a *different* key from access tokens,
  so a challenge can never be presented as a session.
* **Sessions** are short-lived signed access tokens (sixty minutes) paired with
  rotating refresh tokens that are stored only as SHA-256 digests, so a database
  read does not yield a usable session. API keys are stored the same way.
* **Access to production** systems, databases, encryption keys and the network
  is limited to named people with a business need, requires MFA over an
  encrypted channel, and is revoked on termination against a checklist with an
  SLA. These are the infrastructure controls listed in the trust center; this
  repository does not test them, and says so.

### 2.5 Integrity — an append-only record of what the memory holds

Every write into a tenant's memory also appends a leaf to a **per-tenant hash
chain**: content hash, provenance hash, and the previous root, each 32 bytes,
each checked by the database. The chain lets a tenant verify that the facts
Molterra holds are the facts it was given, in the order it was given them, and
that nothing was inserted or removed afterwards. Authentication and
administrative events are written to an audit log whose deletion is blocked by
a database trigger, so an intruder who gains application access cannot erase
their own footprints.

### 2.6 The model boundary — where the new attacks live

Molterra puts retrieved records in front of a language model. That creates a
class of attack older security programs never faced: a record — a CRM note, a
calendar description, an email body — that *contains instructions*, planted by
whoever could write to that record, hoping the model will follow them and
leak, alter or fabricate. The product treats every record as untrusted input at
a hard boundary:

* **Sanitization and budgets.** Every excerpt and title is whitespace-collapsed
  and cut to a fixed character budget before it reaches the prompt, so a record
  cannot flood the context. The current release does not yet strip invisible
  code points at this boundary; the hardening in §3 does, and the finding that
  motivated it is stated below.
* **Control-language detection.** Each line is checked for instruction
  patterns — attempts to redefine the model's role, override prior
  instructions, request exfiltration, or impersonate a system or assistant
  turn. A line that matches is dropped from the excerpt, and a title that
  matches is replaced by nothing. Document text is data, never instructions.
* **Constrained source labels.** The name that tells the model where a record
  came from must be a short machine identifier; anything longer or containing
  other characters collapses to a fixed neutral label. Provider metadata cannot
  carry a sentence into the prompt.
* **Grounding on the way out.** Before a generated sentence is shown as a fact
  about a record, it is verified against the tokens of the approved records it
  claims to come from. A model cannot assert a name, a number or a date the
  records do not contain.
* **Ephemeral tab reads.** Pages the extension reads for ranking are never
  persisted unless the user turns on an explicit "remember what Molterra reads"
  setting, off by default — and then die with that member's forget.

The 991 attacks in this repository are, in the main, attacks on this boundary.

### 2.7 The engineering process as a control

* `main` is protected. Every change lands through a pull request with required
  checks: type and lint gates per subsystem, a **secret scanner**, static
  analysis, and a policy audit that verifies ownership of every changed path.
* Every third-party GitHub Action is **pinned to a commit hash**, not a tag.
* Database migrations are append-only; an applied migration is never edited.
* Every invariant the system depends on is written in a contracts register
  labelled with *how* it is enforced — by the type system, by a failing test,
  or by nothing but review. A guarantee the code does not provide may not be
  claimed. This document is written under the same rule.

## 3. How we attack ourselves

A security program that only describes its defenses has no way to know when
one has quietly stopped working. So the defenses above are attacked
continuously, by code, and the results are published here rather than
summarized.

### 3.1 The corpus

`security/` is a Rust crate that links the product's own fence code and runs
**991 authorized attacks** against it, in one command, on every change:

| Family | Attacks | What is attacked | Against |
|---|---:|---|---|
| Injection | 612 | Instructions planted in records — 18 attacker goals × 34 evasions (homoglyphs, invisible separators, encodings, case and spacing tricks, markup wrappers, forged conversation turns) | the shipped control-language detector, called directly |
| Steganography | 258 | Payloads hidden in text — zero-width characters, bidirectional overrides, variation selectors, the Unicode tag block, combining marks, mathematical alphanumerics, mixed-script look-alikes | the shipped sanitizers and the source-label path |
| Composition | 53 | Sentences that claim more than the records support, or smuggle an instruction through the grounding check | the shipped composition verifier |
| Vault | 54 | Ciphertext tampering, truncation, tag stripping, nonce manipulation, cross-row and cross-tenant transplant, encoding abuse, nonce reuse | a byte-faithful mirror of the AES-256-GCM token store |
| Credential | 14 | Offline recovery of login codes from a stolen database row, preimage ambiguity, comparison timing | a byte-faithful mirror of the login-code hashing |

Every attack has a stable identifier, the attacker's intent, the payload
rendered so that invisible characters are visible, the exact value the target
function returned, and a severity. All 991 are in [`ATTACKS.md`](ATTACKS.md).

### 3.2 Two verdicts per attack

Each attack is run twice and both outcomes are recorded:

* **Shipped** — what the code customers are running today does.
* **Hardened** — what the same payload does against the hardening written in
  response to it, kept in this crate beside the attack that motivated it.

The split is the mechanism that keeps the record honest. A fix is only counted
as landed when the *shipped* column flips to blocked in production code. Until
then the hardened column is a proposal with its evidence attached, and this
document says so.

| Family | Attacks | Shipped blocked | Shipped landed | Hardened blocked | Hardened landed |
|---|---:|---:|---:|---:|---:|
| Injection | 612 | 120 | 492 | 612 | 0 |
| Steganography | 258 | 30 | 228 | 258 | 0 |
| Composition | 53 | 26 | 27 | 51 | 2 |
| Vault | 54 | 49 | 5 | 53 | 1 |
| Credential | 14 | 7 | 7 | 14 | 0 |
| **Total** | **991** | **232** | **759** | **988** | **3** |

**Reading the shipped column.** The shipped detector is built for the
realistic threat — an instruction typed plainly into a record by someone who
compromised a colleague's SaaS account — and it stops every plain-language
attack in the corpus, in the excerpt path, the span path and the composition
path. It stops none of the obfuscated variants, because it matches literally
and does not normalize first. The corpus was built to enumerate exactly those
variants, which is why most of it lands: 34 evasions × 18 instructions is most
of the injection family on its own. Meanwhile the cryptography holds under
every mutation the corpus can produce: 49 of 54 vault attacks are stopped by
the authentication tag itself, not by policy.

**Reading the hardened column.** The hardening normalizes before it matches —
strips the invisible code points, folds look-alike scripts, collapses
separators, decodes the common encodings — then runs the same detection; binds
each ciphertext to its tenant, account and column so a valid ciphertext cannot
be moved between rows; and replaces bare hashing of short codes with a keyed
construction under a secret the database row does not contain. 988 of 991
attacks stop. The three that do not are open by design and discussed below.

### 3.3 Findings and the adaptation loop

An attack that lands on shipped code is a **finding**. The corpus produces 112,
grouped into nine remediation classes in [`PENTEST.md`](PENTEST.md) §5, each
with a CVSS 3.1 estimate, an owner-facing fix, an SLA and a status.
[`FINDINGS.md`](FINDINGS.md) lists every one; [`ADAPTATION.md`](ADAPTATION.md)
records what was built in response and what remains.

The loop is fixed:

1. an attack lands → a finding is opened with the attack as its witness;
2. hardening is written *in this crate*, beside the attack, and the hardened
   verdict must flip to blocked;
3. the hardening is promoted into the product in its own reviewed change, with
   its own entries in the contracts register and a measured false-positive
   cost on ordinary records;
4. the shipped verdict flips; the finding closes; **the attack stays in the
   corpus forever**, so a regression fails CI on the day it happens.

The three most consequential findings, stated plainly:

* **A stored credential was not bound to its row.** The token store encrypted
  correctly but passed no associated data, so a ciphertext valid for one
  account was valid in any account's row. No key or plaintext was needed — only
  a database write. The hardening binds tenant, account and field as
  authenticated associated data; the stored format is unchanged. *(Critical.)*
* **Six-digit login codes could be recovered offline from a stolen row.** The
  server correctly stops online guessing at five attempts, but the digest was
  unkeyed, so a row alone was enough to walk the million-code space. The
  hardening uses HMAC-SHA-256 under a server-side secret, making the row
  insufficient rather than the space larger. *(Critical.)*
* **The Unicode tag block is an invisible alphabet.** `U+E0000–U+E007F` mirrors
  ASCII and survived the sanitizer because it is neither control nor
  whitespace. An instruction or an exfiltrated token could ride into the prompt
  unseen. The hardening strips it at the boundary. *(Critical.)*

### 3.4 What is open, and why

* **Nonce reuse under AES-GCM.** With random 96-bit nonces, a per-key message
  ceiling must be enforced; nothing does yet, and a repeat is catastrophic
  rather than degrading. The fix is a per-key budget with rotation, or a
  misuse-resistant mode (AES-GCM-SIV). Tracked, with a date.
* **Two rows where every word is grounded and the sentence is still false.**
  Token-level grounding cannot see a false proposition built from true tokens.
  Closing it needs proposition-level verification, which is design work, not a
  patch.

### 3.5 Why the corpus can be trusted

A suite that recorded whatever the code did would prove nothing, so:

* **Verdicts are written before they are run.** Each attack states its
  expected shipped and hardened outcome; the test recomputes them. Injection
  and steganography expectations come from an explicit model of what the
  detector *should* do, not from its output.
* **Drift fails in both directions.** An attack that starts landing is a
  regression. An attack that starts being blocked means the register
  overstates a hole. Either fails CI, and fixing it is a reviewer's judgement,
  not an edit to the row.
* **Every attack is deterministic**, asserted by re-running it five times —
  including the vault family, which generates fresh keys and nonces.
* **The hardened column must dominate**, per row: nothing may be blocked
  shipped and land hardened.
* **The hardening must leave real records alone.** A dedicated test requires
  identical verdicts on ordinary prose that resembles an attack — *"the system
  prompt for our support bot needs a rewrite"*, *"please disregard my earlier
  estimate"*, a revenue figure. The false-positive cost is measured, not
  asserted.
* **Everything published is generated** — `FINDINGS.md`, `ATTACKS.md`,
  `attacks/*.md`, `attacks.json`, `findings.json` — and a test fails if the
  committed copy is stale.

## 4. Cryptography

Every primitive the product uses, what it guarantees, what an attacker
provably cannot do if the guarantee holds, and where the implementation falls
short, is in [`CRYPTOGRAPHY.md`](CRYPTOGRAPHY.md) — each written twice, once in
plain language and once formally with the standard it is measured against.

| Purpose | Primitive | Standard |
|---|---|---|
| Credentials and content at rest | AES-256-GCM, 96-bit random nonces, 128-bit tags | NIST SP 800-38D; CNSA 2.0 approved cipher and key size |
| Per-tenant key separation | HKDF-SHA-256 | RFC 5869, NIST SP 800-56C |
| Passwords | Argon2id | RFC 9106 |
| Refresh tokens, API keys at rest | SHA-256 | FIPS 180-4 |
| Webhook authenticity | HMAC-SHA-256, constant-time compare | RFC 2104, FIPS 198-1 |
| Sessions | HS256 JWT, one-hour expiry | RFC 7519 |
| Second factor | TOTP, HMAC-SHA-1, 30 s, replay-step tracking | RFC 6238 |
| Randomness | operating-system CSPRNG | NIST SP 800-90A |
| In transit | TLS, platform-terminated | — |

Three statements are made carefully. The cipher and key size — AES-256 — are
what NSA's CNSA 2.0 suite specifies for national-security systems, and the
review measures every primitive against NIST guidance. Molterra is **not**
FIPS 140-3 validated, has **not** been evaluated for CNSA 2.0 compliance by
anyone but itself, and is **not** post-quantum: none of that is claimed, and
the review lists where a stronger posture (SHA-384 where CNSA 2.0 calls for
it in place of SHA-256, ML-KEM for key establishment, an enforced AES-GCM
message budget) would be required to get there. The review
also maps each topic of a graduate cryptography curriculum — from perfect
secrecy through public-key encryption, signatures, zero knowledge, secure
computation and fully homomorphic encryption — to where it bears on the
product, and says plainly which of those the product does not implement.

## 5. The penetration-testing program

The trust center commits to penetration testing at least annually, with a
remediation plan and SLAs. [`PENTEST.md`](PENTEST.md) is the package a
security team needs to evaluate that commitment:

* **Scope and authorization** — what may be tested, by whom, against what.
  Everything in this repository runs against local code or a loopback-only
  ephemeral instance. Production, staging, customer tenants and third-party
  providers are out of scope by construction; the harness refuses any
  non-loopback target, including user-info and name-resolution tricks.
* **Rules of engagement** — synthetic identities and credentials only, no
  destructive or volumetric testing, evidence retained locally and never
  committed.
* **Methodology** — coverage mapped to OWASP WSTG, OWASP LLM Top 10 and PTES,
  stating for each area what is exercised here and what is not.
* **Toolchain** — Burp Suite, OWASP ZAP, Nikto, SQLmap, Nmap, Dirb/Gobuster,
  Hydra, Metasploit, WFuzz and Wappalyzer/WhatWeb, each mapped to what it
  tests and driven by a runbook or the loopback harness. A tool that was not
  run is recorded as *not run*; no output is ever invented.
* **Remediation register** — nine finding classes with CVSS 3.1 estimates,
  severities, fixes, SLAs and status, each linked to its witnesses.

| Severity | Remediation SLA |
|---|---|
| Critical | 30 days |
| High | 90 days |
| Medium | 90 days |
| Low | next quarter |

Every finding is retested on every CI run of this repository, because the
attack that produced it never leaves the corpus. The continuous program here
does not replace the annual external test; when one is performed, its
findings join the same register with the tester and date named.

## 7. Running it

The crate links the product's fence code by path, so it builds inside the
product source tree, where `security/` sits beside the crate it attacks:

```bash
cd security
cargo run --release --bin redteam            # scoreboard
cargo run --release --bin redteam -- --list  # every attack, both verdicts
cargo run --release --bin redteam -- --write # regenerate the published record
cargo test                                   # the corpus asserts itself
```

This repository is republished from the product source tree after each
accepted change to `security/`; the committed `attacks.json`, `findings.json`
and dossiers are the corpus's output at the published revision, so every
number above is the record of a run, not a claim about one.

## 8. Reporting a vulnerability

If you believe you have found a security issue in Molterra, contact us through
the security channel on the trust center before any public disclosure. Reports
are acknowledged, triaged with the same severity scale as §5, and remediated
within the same SLAs.
